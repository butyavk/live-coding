В обеих задачах код уже написан, тесты падают, а сообщение об ошибке говорит, что видит команда. Ошибки — классические для Python: изменяемый аргумент по умолчанию, конец периода, который не должен входить, деньги во float, слишком широкий `except`. Так что задачи проверяют, знаете ли вы язык и умеете ли читать упавший тест. Они опираются на страницы [Тесты и сложность](/python/testing-and-complexity/) и [Деньги и Decimal](/python/money-and-decimal/).

<Aside type="tip" title="Как тренироваться">
Нажмите «Проверить» до того, как вчитываться в код: упавшие тесты — ваша карта. Возьмите одно падение, найдите его ошибку и назовите её до правки (*"The bug is …, because …"*). Исправьте только её и снова нажмите «Проверить».
</Aside>

## D02. Subscription report

<Task id="d02" />

<Reveal title="Разбор" try>

**Зачем.** Продуктовая команда видит завышенные числа активных и «залипшие» результаты. Это обычные следы общего состояния и неточных границ.

**Ошибки.**

1. Кэш в `active_at` — изменяемый аргумент по умолчанию. `_cache={}` создаётся один раз, живёт между вызовами, и его ключ не учитывает `transactions`. Удалить, а не пытаться починить.
2. `<= t["end_time"]`: конец периода не входит, нужно `<`.
3. Не исключены промо-доступ и возвраты, сделанные до `moment` или ровно в него.
4. `revenue_by_product` складывает деньги во float: 0.10 + 0.20 + 9.99 даёт `10.290000000000001`. Оставить `Decimal` и складывать точно. Округление float в конце только спрятало бы ошибку, а результат остался бы float.

**Как искать.**

- Читать текст падения. «Не меняется при другом списке» — состояние между вызовами. Float там, где ждали `Decimal`, — деньги во float.
- Сначала убрать кэш. Пока он есть, он возвращает результат прошлого вызова, и остальные падения сбивают с толку. За один запуск проверки `test_promo_and_refunds` показывает `{'a': 1}` — остаток от предыдущего теста — вместо настоящего `{'a': 3, 'b': 1}`.

**Сложность.** Один проход, `O(n)` на вызов. Кэш того не стоил: правильному кэшу пришлось бы включать в ключ весь список транзакций.

</Reveal>

## D03. Webhook delivery to merchants

<Task id="d03" />

<Reveal title="Разбор" try>

**Зачем.** Мы доставляем вебхуки на серверы наших продавцов. Часть событий теряется, а воркер, который только что обслужил одного продавца, следующему не отправляет вообще ничего.

**Ошибки.**

1. `seen=set()` по умолчанию создаётся один раз и общий для всех вызовов, которые не передают `seen`. Следующий вызов на том же воркере пропускает id, уже доставленные другому продавцу. Нужно `seen=None` и создавать множество внутри функции.
2. id добавляется в `seen` до успешной отправки, и упавшее событие никогда не повторяется.
3. `except Exception` повторяет и ошибки в нашем payload. Ловить только `TemporaryError`, остальное пропускать наверх.
4. Пауза есть и после последней неудачи. Ждать нужно, только если будет следующая попытка.

**Как искать.** Упавшие тесты показывают ошибки по одной:

- `test_fresh_calls_do_not_share_state` получает `[]` вместо `['x']` — ошибка 1.
- Паузы — `[1.0, 2.0, 1.0, 2.0, 4.0]` вместо `[1.0, 2.0, 1.0, 2.0]` — ошибка 4.
- Для ошибки в payload не поднимается `ValueError` — ошибка 3.
- Когда паузы исправлены, тот же тест на повторы показывает ошибку 2: `b` есть в `seen`, хотя его так и не доставили.

**Сложность.** `O(n log n)` на сортировку по `created_at` плюс не больше `max_attempts` отправок на событие.

**В продакшене.** `seen` живёт в базе или в очереди с подтверждениями, а не в множестве Python. К паузам между повторами обычно добавляют случайный разброс (jitter), чтобы много воркеров не повторяли запросы в один и тот же момент.
