Три задачи работают с медленным или общим ресурсом. Декоратор хранит ответы ограниченное время, а ограничитель пропускает от каждого клиента не больше заданного числа запросов за окно. Третья задача — другая сторона лимита: клиент, который читает все страницы API, ждёт, когда сервер отвечает «слишком много запросов», и повторяет запрос после ошибок сервера. Каждая задача держит немного состояния и зависит от времени, поэтому время приходит снаружи, и тесты им управляют. Задачи опираются на страницы [Декораторы](/python/decorators/), [Окна по времени](/python/time-windows/) и [Ошибки и проверка ввода](/python/errors-and-validation/).

<Aside type="tip" title="Как тренироваться">
Все три задачи получают время снаружи (часы, `now` или функцию `sleep`) — пользуйтесь этим на тренировке. ## P01. TTL cache decorator

<Task id="p01" />

<Reveal title="Разбор" try>

**Зачем.** Кэш ответов медленного внешнего сервиса — например, курса валют — на ограниченное время.

**Идея.** `OrderedDict` «ключ → (stored_at, value)», порядок в нём — порядок использования. При попадании — `move_to_end`; при переполнении `popitem(last=False)` удаляет запись, которой дольше всех не пользовались. Ключ — `(args, tuple(sorted(kwargs.items())))`. Просроченная запись удаляется, когда к ней обращаются.

**Ловушки.**

- Запись действительна, пока `now - stored_at < ttl_seconds`. Ровно на `ttl_seconds` она уже просрочена.
- LRU — это «дольше всех не использовали», а не «раньше всех добавили»: попадание должно переносить ключ в конец.
- Исключение не кэшируется. Сохранять значение только после того, как функция вернула результат.
- Счётчики живут на обёртке: `wrapper.hits` и `wrapper.misses`. `functools.wraps` сохраняет имя и docstring функции.
- Время брать из `clock()`, а не напрямую из `time.monotonic()`: тесты передают поддельные часы.

**Сложность.** Каждая операция — `O(1)`. Память — не больше `max_size` записей. Без `max_size` просроченные записи лежат, пока к ним снова не обратятся.

**Продолжение.** «Это потокобезопасно?» Нет: два потока могут одновременно менять `OrderedDict` или оба промахнуться и оба вызвать функцию. Блокировка (lock) держит словарь в порядке; чтобы функция вызывалась один раз на ключ, нужна блокировка на ключ на время вызова. Кэш, общий для нескольких процессов, живёт снаружи — например, в Redis с TTL.

## P08. Rate limiter for a public API

<Task id="p08" />

<Reveal title="Разбор" try>

**Зачем.** Защитить публичный API: один клиент не должен занять всю его пропускную способность.

**Шаги.** `dict` «ключ → `deque` времён разрешённых запросов». На каждый запрос:

1. Выкинуть слева все времена `<= now - window`.
2. Если осталось меньше `limit`, добавить `now` и вернуть `True`.
3. Иначе вернуть `False`.

**Ловушки.**

- Отклонённые запросы не добавлять: они не считаются.
- Окно — `(now - window, now]`. Запрос ровно через `window` секунд снова проходит, поэтому условие удаления — `<=`.
- Своя `deque` на каждый ключ: ключи независимы.

**Сложность.** Амортизированно `O(1)` на запрос: каждое время добавляется один раз и удаляется один раз. Память — не больше `limit` времён на активный ключ.

**Продолжение.**

- «Миллион клиентов позвонили по разу и больше не вернулись. Что с памятью?» Старые времена выкидываются, только когда тот же ключ приходит снова, поэтому простаивающий ключ навсегда остаётся в `dict` со своей `deque`. Удаляйте ключ, когда его окно опустело: например, раз в N вызовов вычищайте ключи, у которых самое новое время `<= now - window`.
- Token bucket тратит постоянную память на ключ, но пропускает всплески. Фиксированное окно по минутам часов — дёшево, но на стыке двух окон может пропустить 2 × `limit` запросов. В нескольких процессах счётчик живёт в общем хранилище, например в Redis.

</Reveal>

## P13. Fetch every page from the payouts API

<Task id="p13" />

<Reveal title="Разбор" try>

**Зачем.** В каждой интеграции с партнёром или другим сервисом есть этот цикл: страницы, ограничения частоты и сервер, который время от времени падает. Тесты проверяют каждый вызов и каждое ожидание, как это сделал бы разбор инцидента.

**Шаги.**

1. Два уровня: `get_page` для попыток одной страницы и внешний цикл по страницам. Счётчик повторов живёт в `get_page`, поэтому для каждой страницы он начинается заново.
2. В `get_page`: 200 → вернуть json. 429 или 5xx → если повторов не осталось, бросить `ApiError(status)`, иначе подождать и запросить снова. Любой другой статус → сразу `ApiError(status)`.
3. Ожидание перед повтором k: `Retry-After` из ответа 429, найденный без учёта регистра и переведённый в число; иначе `base_delay * 2 ** (k - 1)`.
4. Внешний цикл: параметры с `since.isoformat()` и, начиная со второй страницы, `"cursor"`. Оставлять каждую выплату с новым id и запоминать каждый отправленный курсор. Остановиться, когда `next_cursor is None`; курсор, который уже отправлялся, → `ApiError(None, ...)`.

**Ловушки.**

- Проверка только `next_cursor == cursor` ловит `c1 → c1`, но бесконечно крутится на `c1 → c2 → c1`. Храните множество всех использованных курсоров.
- `sleep("3")`: значение заголовка — строка. Переведите её в число.
- `headers["Retry-After"]` падает на `retry-after`. HTTP/2 присылает все имена заголовков в нижнем регистре.
- Повторять 400 или 404 — пустая трата времени: неверен сам запрос, и в следующий раз он будет так же неверен.
- Один счётчик повторов на весь проход: после одной плохой страницы у всех следующих повторов меньше.
- Ожидание после последней неудачи только откладывает ошибку.
- Запрос следующего курсора после 429 пропускает страницу: в ответе 429 нет данных.

**Проверка.** Назовите ожидания сценария до запуска: 503, затем 429 с `Retry-After: 4`, затем 503, затем 200 дают `[0.5, 4, 2.0]`.

**Сложность.** Один запрос на страницу плюс не больше `max_retries` повторов на страницу. Память — один id на выплату и один курсор на страницу.

**Продолжение.**

- «Десять воркеров делят один лимит. Что изменится?» Каждый отступает сам по себе, и все возвращаются в один и тот же момент. Добавьте к ожиданию случайный разброс (jitter) или поставьте перед клиентом общий token bucket (сравните с P08).
- «Задача упала на странице 400 из 1000.» Сохраняйте последний курсор и уже виденные id как контрольную точку (checkpoint) и продолжайте с неё. Спросите, сколько живёт курсор: просроченный курсор значит начать заново.
- «Почему не постранично по offset?» Новые выплаты сдвигают смещения, пока вы читаете, и элементы пропускаются или повторяются. Курсор отмечает место в данных, а остальное закрывает удаление дублей по id.

**В продакшене.** Ограничьте ожидание по `Retry-After` сверху, пишите в лог каждый повтор со статусом и страницей и ограничьте время всего прохода, а не только каждого запроса.

</Reveal>
